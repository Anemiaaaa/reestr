## Сейчас в работе

**Приоритет 3 — создание задачи с выбором чата.** Клиент к Bitrix готов, дальше
нужны таблица связи «задача ↔ чат» и поле в форме создания задачи.

Приоритет 2 закрыт: пакет `internal/bitrix` читает список чатов, читает
сообщения диалога, снимает разметку и достаёт имена авторов. 45 проверок,
все на подставном портале — живой вебхук в тестах не участвует.

Что взято из API:

| Метод | Зачем |
|---|---|
| `im.recent.list` | список чатов для выпадающего списка при создании задачи |
| `im.dialog.messages.get` | подтяжка сообщений от курсора |
| `user.get` | имя автора, когда его не оказалось в ответе с сообщениями |

Форма ответов снята с живого портала, а не взята из документации, и это
оказалось не лишним. Три вещи устроены не так, как выглядят по названиям:

- **курсор синхронизации — `FIRST_ID`, а не `LAST_ID`.** Проверено:
  `FIRST_ID=42` отдаёт сообщение 46, то есть более новые; `LAST_ID=42` отдаёт
  22, 18, 16, 14, 8 — уходит в историю назад. Клиент, написанный «по смыслу
  названия», листал бы архив и никогда не увидел бы нового сообщения.
  Прежняя запись в этом файле («у каждого чата есть `last_id` — это и есть
  курсор») была неверна дважды: `last_id` в списке чатов — это отметка
  прочитанного, и у чата с сообщениями она равна нулю. Курсор наш, он лежит
  в `chat_links.last_message_id`;
- **идентификатор чата приходит то числом, то строкой:** у личной переписки
  `8`, у группового чата `"chat12"`. Поле `int` отвалилось бы на групповых,
  `string` — на личных, причём с ошибкой на весь список;
- **`params` у сообщения — то объект, то пустой массив `[]`** (так PHP отдаёт
  пустой ассоциативный массив). `map[string]any` падал бы на каждом втором
  сообщении.

Ещё две особенности, которые видно только на живых данных:

- **бот отличается по флагу `user.bot`, а не по типу элемента:** у диалога с
  «Битрикс24 Гид» поле `type` равно `"user"`, как у обычной переписки;
- **в личном чате портала лежит адрес вебхука** — портал сам присылает его при
  создании. Поэтому весь текст из Bitrix проходит через `Redact` до того, как
  станет источником, включая подпись чата в выпадающем списке.

Даты приходят в ISO с `+03:00`. Сервис без настроенного Bitrix остаётся
работоспособным: список чатов пуст, задача всё равно создаётся.

Таблицы `chat_links` и `raw_messages` появятся в приоритете 3 — это первое
изменение схемы на живых данных, то есть и первая нумерованная миграция.

Подробности по каждой:

**3. Создание задачи с выбором чата.** Поле «Чат Bitrix24» — выпадающий
список из `GET /api/bitrix/chats`. Выбранный чат закрепляется за задачей в
таблице `chat_links` (`task_id`, `dialog_id`, `last_message_id`,
`last_sync_at`).

**4. Подтяжка сообщений.** Забираем от курсора, кладём в `raw_messages`
как есть, курсор сдвигаем. Повторная подтяжка не должна создавать дублей —
защита через `ExternalRef.Key()` вида `система:чат:сообщение`, уникальный
индекс уже предусмотрен схемой. В источники попадают не все сообщения, а
только те, на которые сослался разбор.

**6. Обновление из КМ.** Кнопка «Добавить обновление из КМ»: PM вставляет
фрагмент Капитанского мостика, тот сохраняется отдельным источником вида
`bridge` с датой события и автором. Автоматический разбор КМ на первом
этапе не делаем, но шов под него уже заложен: у источника есть
необязательные `TaskID` (пусто — значит общий для нескольких задач) и
`ParentID` (фрагмент → документ). Добавить разбор позже можно будет, не
переделывая схему.

**7. Анализ через модель.** Пакет `internal/analyst/claude` рядом с уже
существующим `manual`. Модель обязана возвращать ответ строгой схемой —
проверено, работает. Правила, которые закладываются в проверку, а не
только в промпт:

- каждая цитата обязана дословно встречаться в источнике, иначе факт
  отбрасывается — это защита от выдумывания;
- арифметику модель не считает вообще: проценты и суммы считает Go, модель
  только извлекает факты со ссылкой на источник;
- факт и предположение разделены, у каждого значения есть происхождение:
  `↩` цитата, `→` вывод, `∑` расчёт, `?` данных нет;
- аналитик называет даты, а не число дней.

**8. Пересборка в 20:00.** По Москве — часовой пояс взят из портала
Bitrix, совпадает. Если с прошлой сборки ничего не изменилось, новая
версия не создаётся: одинаковые версии множить нельзя. Если модель или API
недоступны — предыдущий срез остаётся на месте, пустым не подменяется,
ошибка пишется в `rebuild_runs`, задача остаётся на последнем удачном
срезе.

**9. История версий.** Список версий с датами, просмотр одной версии,
сравнение двух в виде «Было → Стало» по разделам. На `Store` для этого
нужны метод получения конкретной версии и метод списка версий.

**10. Дизайн.** Замечание заказчика: интерфейс перегружен, непонятно, что
к какому блоку относится. Правка вёрстки и группировки. Ограничение,
которое нельзя нарушать: тексты источников и цитаты из аудита выводятся
только через `textContent`, никогда через `innerHTML` — это чужой текст,
пришедший из переписки.

## Что уже готово

**Архитектура.** Зависимости направлены внутрь: `domain` не знает ни о
базе, ни о HTTP и не импортирует ничего кроме стандартной библиотеки;
`ru`, `store`, `analyst`, `service`, `httpapi` зависят от него, но не он от
них. Около 7300 строк.

| Пакет | Что делает |
|---|---|
| `internal/domain` | задача, источник, срез, значение с провенансом, процессы, план |
| `internal/service` | сборка среза, версии, идентификаторы |
| `internal/store` | интерфейс хранилища, без `Update` и `Delete` |
| `internal/store/jsonstore` | реализация на JSON-файле |
| `internal/store/pgstore` | реализация на PostgreSQL |
| `internal/store/storetest` | общий контракт: один набор проверок на оба хранилища |
| `internal/analyst` | контракт разбора и ручная реализация на реальном аудите |
| `internal/httpapi` | API, схемы, представления |
| `internal/ru` | падежи и числа по-русски |
| `internal/config` | чтение `.env` |
| `web` | фронт, вшит в бинарник через `embed.FS` |

**PostgreSQL** (приоритет 1). Шесть таблиц, схема применяется при запуске:
все выражения idempotent, отдельный шаг миграции появится с первым
изменением схемы на живых данных. Выбор хранилища — настройка: без
`DATABASE_URL` сервис работает на файле, и без базы его по-прежнему можно
запустить.

Срез хранится дважды: как JSONB целиком (версия обязана быть
самодостаточной) и отдельными плоскими полями — этап, готовность, дата
сборки — чтобы список версий строился запросом, без разбора JSON на каждую
строку.

Правило по датам во всей схеме: нулевое время в Go — это `NULL`, а не
«01.01.0001». «Дата не заполнена» и «первое января первого года» — разные
утверждения, и срез обязан их различать, иначе в отчёте появится
выдуманное число. У задачи АУРА дата постановки не названа ни в переписке,
ни в аудите — она и лежит как `NULL`, оставаясь пробелом среза.

**Общий контракт хранилищ.** «Файл и база взаимозаменяемы» было обещанием,
записанным в комментариях. Теперь это проверяет один набор тестов на оба
бэкенда — `internal/store/storetest`, тринадцать проверок. До него у
каждого хранилища был свой набор, и оба свои проверки проходили; расхождений
от этого не было меньше — их просто было нечем увидеть. Нашлось восемь, в
том числе:

- база отвергала нулевое время, которое файл принимал, — на трёх полях
  сразу;
- существование задачи при записи проверялось в базе, но не в файле, — и
  по-разному для фактов, схем и срезов;
- порядок выдачи источников различался;
- срез, сославшийся на один источник дважды, в файле сохранялся, а в базе
  падал на первичном ключе.

Все восемь закрыты, и закрытие проверяется, а не утверждается.

**Модель источников** (приоритет 5). У источника есть вид (переписка, ТЗ,
аудит, мостик, документ, заметка), автор, дата события, дата загрузки и
ссылка на оригинал в Bitrix. Вид и происхождение — разные поля намеренно:
вид отвечает «что это за материал», ссылка — «откуда взялся».

Главное решение здесь: **список источников версии выводится из среза, а не
берётся со слов модели.** В версию попадают только те источники, на
которые срез действительно ссылается хотя бы одним полем. Сказать «я
использовал эти сообщения» дёшево, сослаться на них в конкретном поле —
нет. Рядом хранится число рассмотренных, чтобы был виден объём материала:
«рассмотрено 100, использовано 7».

**Ручной разбор.** `internal/analyst/manual` собирает срез из настоящего
аудита заказчика — это позволило проверить сборку и вёрстку на реальных
данных до подключения модели.

## Известные дефекты

**Пересборка без изменений множит и версии, и факты.** Измерено на чистой
базе: после посева 32 факта и одна версия, после одной пересборки тем же
материалом — 64 факта (уникальных по-прежнему 32) и вторая версия,
совпадающая с первой.

Содержание среза при этом не портится: факты кладутся в отображение по
полю, и повтор перекрывает сам себя тем же значением. Портится другое —
журнал фактов растёт на 32 строки за каждое нажатие кнопки, а история
версий заполняется пустыми различиями. Это прямо против требования «если
ничего не изменилось — не размножать одинаковые версии».

Решение принимать до приоритета 8, потому что от него зависит, где живёт
проверка. Если в `Service.Rebuild` — её получают и ночной запуск, и кнопка;
если только в планировщике — кнопка останется дырой. Первое выглядит
правильнее, но это решение заказчика: возможно, ручная пересборка нужна
именно как «собери заново, что бы там ни было».

export PATH="/c/Users/amiri/sdk/go1.26.6/bin:$PATH"

**PostgreSQL 17.11** в контейнере `reestr-pg`, порт **5433** — потому что

```
postgres://reestr:reestr@127.0.0.1:5433/reestr?sslmode=disable
```

`psql` в PATH нет, заходить через `docker exec reestr-pg psql`.

**Bitrix24** — вебхук проверен на живом портале: аккаунт админский, права
`im`, `task`, `tasks`, `tasks_extended`, `user`, часовой пояс портала
Europe/Moscow. Чаты читаются, сообщения читаются. Курсор синхронизации ведём
сами — `FIRST_ID` от последнего сохранённого сообщения; `last_id` в списке
чатов к этому отношения не имеет, это отметка прочитанного.

**Модель** — ключ проверен, доступна `claude-opus-4-8`. Проверено то, на
чём держится разбор: строгая схема ответа соблюдается, кириллица проходит
без потерь в обе стороны, цитата возвращается дословно, дата нормализуется
в `ГГГГ-ММ-ДД`.

Адрес сервиса по умолчанию **127.0.0.1:8080**, не `:8080`. Только петля, а
не все интерфейсы: в реестре лежат аудиты заказчиков с оборотами и
сметами.

Настройки — в `.env`, форма и пояснения — в `.env.example`. Секреты в
репозиторий не попадают. `ANTHROPIC_BASE_URL` вынесен в настройку
намеренно: переход со шлюза на прямой Anthropic должен быть правкой одной
строки, а не кода.

Запуск:

```
go run ./cmd/reestr
```

Проверка:

```
go build ./... && go test ./...
```
